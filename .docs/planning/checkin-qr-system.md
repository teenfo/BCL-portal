## 1. 개요 및 배경

### 1.1 목적
키오스크에서 회원이 QR 코드를 스캔하여 체크인할 때, **QR 생성 로직과 인증 로직이 불일치**하여 
항상 "유효하지 않은 QR 코드" 에러가 발생하는 문제를 해결한다.

또한 **체크인 유형을 2가지로 구분**하여 실제 피트니스 센터 운영에 맞는 체크인 시스템을 구축한다:
1. **시설 출석 체크인** — "오늘 짐에 왔습니다" (예약 무관)
2. **수업 체크인** — "예약한 수업에 참석합니다" (booking 연결)

### 1.2 현재 상태 (As-Is)
| 항목 | 상태 | 비고 |
|------|------|------|
| QR 생성 (앱) | ❌ 불완전 | 랜덤 토큰만 생성, 회원 정보 미포함, DB 미저장 |
| QR 인증 (키오스크) | ❌ 불일치 | JSON 파싱 또는 qr_codes 테이블 조회 기대 |
| 시설 출석 체크인 | ❌ 미동작 | QR 인증 실패로 체크인 불가 |
| 수업 체크인 | ❌ 미구현 | booking/session 연결 로직 없음 |
| checkins 테이블 | ✅ 구조 준비됨 | booking_id, session_id 컬럼 존재 |
| qr_codes 테이블 | ⚠️ 스키마만 존재 | 실제 활용 로직 없음 |

### 1.3 핵심 제약 조건
| 항목 | 내용 |
|------|------|
| CSR 전용 | 서버 렌더링 금지, 모든 로직 클라이언트에서 처리 |
| RLS 필수 | 체크인 기록은 본인/관리자만 접근 가능 |
| anon key | QR 검증 시에도 Service Role Key 사용 금지 |
| 오프라인 대비 불필요 | HTTPS 환경, 항상 온라인 전제 |

## 2. 현재 문제 진단 (As-Is)

### 2.1 QR 생성 흐름 (앱)
```
회원 앱 (/apps/checkin)
     │
     ▼
generateToken()
     │ "BCL-" + 랜덤20자 + "-" + timestamp(base36)
     │  예: "BCL-aBcDeFgHiJkLmNoPqRsT-m1abc2d"
     ▼
<QRCodeSVG value={qrToken} />
     │
     ▼
QR 코드 표시 (5분 만료, 자동 갱신)
     │
     ❌ DB에 토큰 저장 안 함
     ❌ 회원 ID 포함 안 함
     ❌ 시설 ID 포함 안 함
```

### 2.2 QR 인증 흐름 (키오스크)
```
키오스크 (/kiosk/scan)
     │ QR 스캔
     ▼
processQRCode(code)
     │
     ├── 1차: JSON.parse(code)  → { member_id, facility_id }
     │    ❌ 실패 (랜덤 문자열은 JSON이 아님)
     │
     └── 2차: supabase.from('qr_codes').select().eq('code', code)
              ❌ 실패 (토큰이 DB에 저장되지 않았으므로)
     │
     ▼
"유효하지 않은 QR 코드입니다" 에러 ← 항상 이 결과
```

### 2.3 문제점 요약
| # | 문제 | 원인 | 영향 |
|---|------|------|------|
| 1 | QR 코드에 회원 정보 없음 | generateToken()이 랜덤 문자열만 생성 | 키오스크가 회원 식별 불가 |
| 2 | QR 토큰이 DB에 저장 안 됨 | 앱에서 DB insert 로직 없음 | 키오스크가 토큰 조회 불가 |
| 3 | 생성/인증 프로토콜 불일치 | 앱은 문자열, 키오스크는 JSON 기대 | 파싱 실패 |
| 4 | 수업 체크인 미지원 | booking 연결 로직 없음 | 수업 출석 관리 불가 |

## 3. 개선 설계 (To-Be)

### 3.1 핵심 설계 원칙
1. **QR 코드 = 회원 식별 토큰** — QR에 member_id를 포함하여 키오스크가 회원을 즉시 식별
2. **서버에서 체크인 유형 판단** — 키오스크가 아닌 DB 쿼리로 수업 예약 여부를 자동 판단
3. **시간 기반 보안** — 토큰에 타임스탬프 포함하여 만료된 QR 코드 거부
4. **DB 저장 불필요** — 토큰 자체에 정보를 인코딩하여 DB 조회 없이 검증

### 3.2 QR 코드 페이로드 설계

QR 코드에 인코딩할 JSON:
```json
{
  "mid": "uuid-of-member",      // member_id (members 테이블의 id)
  "fid": "uuid-of-facility",    // facility_id
  "ts": 1771503000,             // 생성 타임스탬프 (Unix epoch seconds)
  "v": 1                         // 버전 (향후 확장용)
}
```

> **보안 참고**: 이 QR 코드는 내부 키오스크(동일 네트워크)에서만 사용되므로
> 서명/암호화 없이 JSON 페이로드로도 충분합니다.
> 타임스탬프(ts)로 5분 만료를 검증하여 QR 코드 재사용을 방지합니다.

### 3.3 개선된 전체 흐름

```
┌─────────────────────────────────────────────────────────────┐
│  📱 회원 앱 (/apps/checkin)                                  │
│                                                             │
│  1. auth.getUser() → user.id 획득                           │
│  2. members 테이블에서 member_id 조회 (user_id 기준)          │
│  3. 시설 정보 (단일 시설이면 하드코딩 or facilities 첫 번째)    │
│  4. QR 페이로드 생성:                                        │
│     { mid: member.id, fid: facility.id, ts: now(), v: 1 }  │
│  5. QRCodeSVG(JSON.stringify(payload))                      │
│  6. 5분 타이머 → 자동 갱신 (새 ts)                           │
└─────────────────────┬───────────────────────────────────────┘
                      │ QR 코드 스캔
                      ▼
┌─────────────────────────────────────────────────────────────┐
│  🖥️ 키오스크 (/kiosk/scan)                                  │
│                                                             │
│  1. JSON.parse(qrCode) → { mid, fid, ts, v }               │
│  2. 타임스탬프 검증: (now - ts) < 300초 (5분)                 │
│  3. members 테이블 조회 (mid로 회원 존재 확인)                 │
│  4. 수업 예약 확인:                                          │
│     bookings WHERE member_id = mid                          │
│              AND status = 'booked'                          │
│              AND session.session_date = today               │
│              AND 현재시간이 수업 시작 ±30분 이내              │
│                                                             │
│  ┌── 예약 있음 ──────────────────┐  ┌── 예약 없음 ─────────┐ │
│  │ 🎓 수업 체크인                │  │ 🏢 시설 출석 체크인   │ │
│  │ checkins INSERT:              │  │ checkins INSERT:     │ │
│  │   member_id = mid             │  │   member_id = mid    │ │
│  │   facility_id = fid           │  │   facility_id = fid  │ │
│  │   booking_id = booking.id     │  │   booking_id = null  │ │
│  │   session_id = session.id     │  │   session_id = null  │ │
│  │   checkin_method = 'kiosk'    │  │   checkin_method     │ │
│  │                               │  │     = 'kiosk'        │ │
│  │ booking.status → 'attended'   │  │                      │ │
│  └───────────────────────────────┘  └──────────────────────┘ │
│                                                             │
│  5. 성공 화면 → 회원 이름 + 체크인 유형 표시                   │
└─────────────────────────────────────────────────────────────┘
```

## 4. 데이터베이스 변경 (필요 시)

### 4.1 마이그레이션 SQL
기존 `checkins` 테이블은 이미 필요한 컬럼(member_id, facility_id, booking_id, session_id)을 
모두 보유하고 있으므로 **스키마 변경이 필요 없습니다.**

`qr_codes` 테이블도 이번 설계에서는 **사용하지 않습니다** (QR 토큰을 DB에 저장하지 않는 방식).

### 4.2 RLS 정책 확인
```sql
-- 키오스크에서 체크인 INSERT를 위한 정책 확인 필요
-- 키오스크는 인증된 사용자(admin)로 로그인하여 사용하므로,
-- admin 역할의 INSERT 권한이 있는지 확인

-- members 테이블 SELECT (회원 정보 조회)
-- → 기존 RLS에서 인증 사용자의 SELECT 허용 필요

-- bookings 테이블 SELECT (예약 정보 조회)
-- → admin이 모든 예약을 조회할 수 있어야 함

-- checkins 테이블 INSERT
-- → admin이 체크인 기록을 삽입할 수 있어야 함
```

> ⚠️ 키오스크 인증 방식에 따라 RLS 정책 조정이 필요할 수 있음.
> 현재 키오스크는 **별도 인증 없이 공개 접근**하고 있으므로,
> `anon` 역할의 INSERT 권한 또는 키오스크 전용 서비스 계정이 필요합니다.

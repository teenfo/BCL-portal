# Feature Planning Workflow (/plan)

이 워크플로우는 사용자의 요청을 받아 **기획 문서를 작성**하는 기획자(Planner) 전용 워크플로우입니다.
현황 분석 → 설계 → 관점 배분 → 기획 문서 저장 → (선택) 블루프린트 등록까지의 전체 기획 프로세스를 수행합니다.

---

## 🤖 전담 관점

> **이 워크플로우의 모든 단계는 🏛️ Architect 관점에서 수행한다.**
> 기획은 아키텍처적 판단이 필요하므로, 다른 관점으로 위임하지 않는다.
> **권장 모델**: Gemini 3 Pro (High) — 1M 컨텍스트로 전체 코드/문서 분석 가능

| 단계 | 관점 | 핵심 역할 |
|:-----|:-----|:---------|
| 1. 요구사항 수집 | 🏛️ **Architect** | 사용자 요청 파악, 범위 확정 |
| 2. 현황 분석 | 🏛️ **Architect** | 코드/DB/문서 분석, 중복 확인 |
| 3. 설계 | 🏛️ **Architect** | As-Is → To-Be 설계, 아키텍처 결정 |
| 4. 기획 문서 작성 | 🏛️ **Architect** | 표준 템플릿 기반 문서 작성 |
| 5. 품질 검증 | 🏛️ **Architect** | 체크리스트 기반 자체 검증 |
| 6. (선택) 블루프린트 등록 | 🏛️ **Architect** | `/plan-to-blueprint` 실행 |

---

## 핵심 원칙

> **기획 = 개발의 전제 조건**
>
> 1. 기획 문서 없이 개발을 시작하지 않는다.
> 2. 기획 문서는 반드시 `.docs/planning/`에 저장한다.
> 3. 기획은 코드를 변경하지 않고, **문서만 생성/수정**한다.
> 4. 기획 완료 후 `/plan-to-blueprint` 워크플로우로 블루프린트에 등록한다.
> 5. **기획은 한번에 완료하지 않아도 된다.** 초안(Draft) → 반복 확장 → 최종 승인(Approved) 흐름을 따른다.
> 6. 기획 세션이 중단될 때마다 **현재 진행 상황을 문서 내 Planning Log에 기록**한다.

---

## 문서 상태 관리 (Status Lifecycle)

```
Draft (초안)  →  In Progress (작성 중)  →  Approved (승인 — 개발 대기)
  ↑                    │
  └────────────────────┘  (반복 가능: 세션 중단 → 재개)
```

| Status | 의미 | 다음 액션 |
|--------|------|----------|
| **Draft** | 초기 아이디어/요구사항만 정리됨 | → 현황 분석, 설계 진행 |
| **In Progress** | 분석/설계가 진행 중이나 일부 섹션 미완성 | → 미완성 섹션 작성 계속 |
| **Approved** | 모든 섹션 완성. 개발 착수 가능 | → `/plan-to-blueprint` 등록 |

> ⚠️ **Status가 `Approved`가 아닌 기획 문서는 `/plan-to-blueprint`로 등록하지 않는다.**

## 전체 파이프라인

```
┌────────────────────────────────────────────────────────┐
│  📝 /plan (이 워크플로우) — 반복 가능                     │
│  요구사항 → 분석 → 설계 → 기획서 작성 → .docs/planning/  │
└──────────────────┬─────────────────────────────────────┘
                   │ Status = Approved
                   ▼
┌────────────────────────────────────────────────────────┐
│  📋 /plan-to-blueprint (후속 워크플로우)                  │

└──────────────────┬─────────────────────────────────────┘
                   │ 등록 완료
                   ▼
┌────────────────────────────────────────────────────────┐
│  🚀 /develop (개발 실행 워크플로우)                       │
│  블루프린트 Priority → Phase별 개발                      │
└────────────────────────────────────────────────────────┘
```

## 단계별 절차

### 0️⃣ 실행 모드 판별 (신규 vs 이어쓰기)

`/plan` 호출 시 가장 먼저 `.docs/planning/` 폴더를 스캔한다.

// turbo
```bash
ls .docs/planning/
```

| 조건 | 액션 |
|------|------|
| 사용자가 특정 파일 지정 | 🔄 **이어쓰기 모드** — 해당 파일 로드 |
| Draft/In Progress 파일 존재 | 사용자에게 목록 제시 → 선택 또는 신규 |
| 파일 없음 / 모두 Approved | 🆕 **신규 모드** — Step 1부터 진행 |

#### 🔄 이어쓰기 모드
1. 기존 문서의 **Status**와 **Planning Log** 읽기
2. 미완성 섹션 목록을 사용자에게 보고
3. 미완성 섹션부터 작업 이어가기
4. 사용자가 새 요구사항 추가 시 기존 내용에 통합

---

### 1️⃣ 요구사항 수집 및 범위 확정

사용자의 요청을 정확히 이해하고 기획의 범위를 확정한다.

1. 사용자 요청의 **핵심 목적(What/Why)**을 파악한다
2. 모호한 부분이 있으면 **반드시 사용자에게 질문**한다 (추측 금지)
3. 범위가 너무 넓으면 **분할을 제안**한다

> ⚠️ **사용자가 충분한 정보를 제공한 경우, 확인 질문 없이 바로 분석으로 진행 가능**

---

### 2️⃣ 현황 분석 (As-Is)

기획 대상과 관련된 프로젝트의 현재 상태를 철저히 분석한다.

// turbo
1. **기존 기획 중복 확인**:
   ```bash
   ls .docs/planning/
   ls .docs/archive/planning/
   ```
   > 동일/유사 기획이 이미 존재하면 사용자에게 보고하고 중단한다.

// turbo
2. **관련 코드 분석**:
   ```bash
   grep -rl "{관련키워드}" src/app/ --include="*.tsx"
   ```

// turbo
3. **DB 스키마 분석**:
   ```bash
   cat .docs/database-reference.md
   ```

// turbo
4. **Sitemap 및 블루프린트 확인**:
   ```bash
   cat .docs/sitemap/README.md
   cat .docs/project-blueprint.md
   ```

### 3️⃣ 설계 (To-Be)

**설계 원칙**:
- CSR 기반 아키텍처 (SSR 금지)
- RLS 필수 (모든 새 테이블)
- Client SDK는 anon key만 사용
- 기존 패턴 활용, 최소 변경 원칙

**설계 포함 사항**:
- 데이터 흐름 다이어그램 (ASCII)
- DB 변경 사항 (실행 가능한 SQL)
- UI 변경 사항 (화면 레이아웃 ASCII)
- 영향 범위 분석

---

### 4️⃣ 관점 배분 및 Phase 설계

| 관점 | 권장 모델 | 담당 작업 |
|------|----------|----------|
| 🏛️ **Architect** | Gemini 3 Pro (High) | 설계, 구조 결정, 최종 승인 |
| 💎 **Senior Dev** | Claude Opus 4.6 | DB 스키마, RLS, 복잡한 비즈니스 로직 |
| 💻 **Developer** | Claude Sonnet 4.6 | API, 일반 로직, 테스트/QA |
| 🎨 **UI Developer** | Gemini 3 Pro (Low) | 화면 UI/UX, 디자인 일관성 관리 |
| ⚡ **Specialist** | Gemini 3 Flash | 실시간 기능, 성능 최적화 |

**Phase 설계 규칙**:
1. Phase 1은 항상 인프라/DB 작업 (💎 Senior Dev)
2. UI Phase는 DB Phase 이후에 배치
3. 마지막 Phase는 항상 "문서 동기화" (🏛️ Architect)
4. 각 Phase는 독립 빌드 가능해야 한다
5. Phase 당 예상 공수 명시

### 6️⃣ 품질 검증 (전체 완성 시만)

모든 섹션이 작성된 경우에만 수행. 통과 시 Status를 `Approved`로 변경.

```
기획 문서 품질 체크리스트:
[ ] Status 헤더가 정확히 기입됨
[ ] As-Is 현황 분석이 실제 코드/DB를 반영함
[ ] To-Be 설계에 ASCII 다이어그램이 포함됨
[ ] DB 변경이 있으면 실행 가능한 SQL 포함
[ ] RLS 정책이 누락되지 않음
[ ] 영향 범위 분석이 실제 파일 경로를 포함
[ ] 모든 Phase에 담당 관점이 명시됨
[ ] 마지막 Phase가 "문서 동기화" (Architect)
[ ] 테스트 시나리오: 정상 ≥ 3건, 예외 ≥ 2건
[ ] 블루프린트 등록용 체크리스트(섹션 9)가 존재함
```

### 7️⃣ 결과 보고

#### 기획 완료 시 (Status: Approved)
블루프린트 등록 옵션 제안:
1. `/plan-to-blueprint` 실행 → 블루프린트 등록
2. 사용자 리뷰 후 등록
3. 추가 기획 작성

#### 세션 중단 시 (Status: Draft / In Progress)
1. 문서 내 `## 12. Planning Log`에 세션 기록 추가
2. Status를 `Draft` 또는 `In Progress`로 설정
3. `Last Updated` 날짜 갱신
4. `commit-bot` 스킬로 문서 커밋
5. "이어서 작업하려면 `/plan` 실행" 안내

## ⚠️ 주의사항

- ❌ 기획 문서 작성 중 코드를 변경하지 않는다
- ❌ 현황 분석 없이 기획 문서를 작성하지 않는다
- ❌ 기존 기획과 중복되는 기획을 새로 작성하지 않는다
- ❌ 사용자의 요구사항이 불명확한데 추측으로 기획하지 않는다 (반드시 확인)
- ✅ 기획 문서는 항상 `.docs/planning/`에 저장한다
- ✅ 실제 코드/DB를 분석한 결과를 As-Is에 반영한다
- ✅ 모든 DB 변경에 실행 가능한 SQL을 포함한다
- ✅ 기획 완료 후 `commit-bot` 스킬로 문서만 커밋한다

# Feature Planning Skill (feature-planning)

이 스킬은 **기능 기획의 전 과정**을 담당합니다.
사용자의 요청 또는 프로젝트 분석 결과를 바탕으로, 체계적인 기획 문서를 작성하여 `.docs/planning/` 폴더에 저장합니다.

> **⚠️ 이 스킬의 모든 단계는 🏛️ Architect (Opus)가 전담 수행한다.**
> 기획 작성은 아키텍처적 판단이 필요하므로, 다른 에이전트에게 위임하지 않는다.

---

## 언제 이 스킬을 사용하는가?

- 사용자가 새로운 기능을 요청했을 때
- 기존 기능의 아키텍처 변경이 필요할 때
- 기술 부채를 해결하기 위한 리팩토링 계획이 필요할 때
- 외부 서비스/API 연동을 설계할 때
- 보안/성능 개선이 필요할 때

---

## 핵심 원칙

> **기획 = 개발의 전제 조건**
> 
> 1. 기획 문서 없이 개발을 시작하지 않는다.
> 2. 기획 문서는 반드시 `.docs/planning/`에 저장한다.
> 3. 기획은 코드를 변경하지 않고, **문서만 생성/수정**한다.
> 4. 기획 완료 후 `/plan-to-blueprint` 워크플로우로 블루프린트에 등록한다.
> 5. **기획은 한번에 완료하지 않아도 된다.** 초안(Draft) → 반복 확장 → 최종 승인(Approved) 흐름을 따른다.
> 6. 기획 세션이 중단될 때마다 **현재 진행 상황을 문서 내 Planning Log에 기록**한다.

---

## 문서 상태 관리 (Status Lifecycle)

기획 문서는 다음 상태 흐름을 따른다:

```
Draft (초안)  →  In Progress (작성 중)  →  Approved (승인 — 개발 대기)
  ↑                    │
  └────────────────────┘  (반복 가능: 세션 중단 → 재개)
```

| Status | 의미 | 다음 액션 |
|--------|------|----------|
| **Draft** | 초기 아이디어/요구사항만 정리됨. 분석·설계 미완료. | → 현황 분석, 설계 진행 |
| **In Progress** | 분석/설계가 진행 중이나 일부 섹션 미완성. | → 미완성 섹션 작성 계속 |
| **Approved** | 모든 섹션 완성. 개발 착수 가능. | → `/plan-to-blueprint` 등록 |

> ⚠️ **Status가 `Approved`가 아닌 기획 문서는 `/plan-to-blueprint`로 등록하지 않는다.**
> `Draft` 또는 `In Progress` 문서는 `.docs/planning/`에 남아있으며, 언제든 이어서 작성할 수 있다.

## 스킬 실행 절차

### 0️⃣ 실행 모드 판별 (신규 vs 이어쓰기)

`/plan`이 호출되면 가장 먼저 **실행 모드를 판별**한다.

```
.docs/planning/ 폴더 스캔
    │
    ├── 사용자가 특정 기획 파일을 지정함?
    │     └── YES → 🔄 이어쓰기 모드 (해당 파일 로드)
    │
    ├── .docs/planning/에 Draft / In Progress 파일이 있음?
    │     └── YES → 사용자에게 목록 제시, 선택 요청
    │               ├── 기존 파일 선택 → 🔄 이어쓰기 모드
    │               └── 새로 작성 선택 → 🆕 신규 모드
    │
    └── 파일 없음 (또는 모두 Approved)
          └── 🆕 신규 모드
```

#### 🆕 신규 모드
→ **Step 1️⃣**부터 순서대로 진행 (아래 절차)

#### 🔄 이어쓰기 모드
→ **기존 파일을 로드**한 후 다음을 수행:
1. 기존 문서의 **Status**와 **Planning Log**를 읽는다
2. Planning Log의 마지막 세션 기록에서 **남은 작업(TODO)**을 확인한다
3. 미완성 섹션을 **사용자에게 보고**한다:
   ```
   📄 기존 기획 문서 로드:
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
     파일:   .docs/planning/{파일명}.md
     Status: {Draft / In Progress}
     버전:   {N}.0.0
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
     ✅ 완성된 섹션:  {목록}
     📝 미완성 섹션:  {목록}
     💬 이전 세션 메모: {Planning Log의 마지막 TODO}
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   ```
4. 미완성 섹션부터 작업을 이어간다
5. 사용자가 **새로운 요구사항을 추가**한 경우, 기존 내용에 통합한다

---

### 1️⃣ 요구사항 수집 및 명확화

사용자의 요청을 정확히 이해하고 기획의 범위를 확정한다.

**수행 항목**:
1. 사용자 요청의 핵심 목적(What/Why)을 파악한다
2. 모호한 부분이 있으면 **반드시 사용자에게 질문**한다
3. 범위가 너무 넓은 경우 **분할 제안**한다

**확인 질문 예시** (필요 시):
```
- 이 기능의 주요 사용자는 누구인가? (회원/관리자/코치)
- 기존 기능 중 영향을 받는 것이 있는가?
- 외부 서비스 연동이 필요한가?
- 긴급도는? (즉시 개발 / 차후 개발)
```

> ⚠️ **사용자가 충분한 정보를 제공한 경우, 확인 질문 없이 바로 분석으로 진행 가능**

---

### 2️⃣ 현황 분석 (As-Is)

기획 대상과 관련된 프로젝트의 현재 상태를 철저히 분석한다.

**필수 분석 항목**:

| 분석 대상 | 확인 파일/위치 | 목적 |
|-----------|---------------|------|
| **기존 구현** | `src/app/**/*.tsx` | 현재 코드가 어떻게 동작하는지 파악 |
| **DB 스키마** | `.docs/database-reference.md`, Supabase | 관련 테이블/컬럼/RLS 현황 |
| **Sitemap** | `.docs/sitemap/**/*.md` | 관련 화면/라우트 구조 |
| **블루프린트** | `.docs/project-blueprint.md` | 이미 등록된 관련 작업 확인 |
| **기존 기획** | `.docs/planning/`, `.docs/archive/planning/` | 중복 기획 방지 |
| **보안 규칙** | `.docs/security/**/*` | 보안 제약 조건 |

**분석 수행 방법**:
```bash
# 관련 파일 검색
find src/app -name "*.tsx" | grep -i {관련키워드}

# DB 스키마 참조
cat .docs/database-reference.md | grep -A 20 {테이블명}

# 기존 기획 중복 확인
ls .docs/planning/
ls .docs/archive/planning/
```

> ⚠️ **기존에 동일/유사 기획이 이미 존재하면, 새로 작성하지 않고 사용자에게 보고한다.**
> 예: "이미 `.docs/archive/planning/payment-system.md`에 해당 기획이 등록되어 있습니다."

---

### 3️⃣ 설계 (To-Be)

분석 결과를 바탕으로 개선 방안을 설계한다.

**설계 원칙**:
1. **CSR 기반** 아키텍처 준수 (SSR 사용 금지)
2. **RLS 필수** — 모든 새 테이블에 RLS 정책 포함
3. **Supabase SDK** — Client에서는 anon key만 사용
4. **기존 패턴 따르기** — 프로젝트에서 이미 사용 중인 패턴/컴포넌트 활용
5. **최소 변경 원칙** — 기존 코드에 미치는 영향 최소화
6. **실행 가능한 SQL** — DB 변경이 있으면 실제 실행 가능한 SQL 작성

**설계 포함 사항**:
- 핵심 설계 원칙 (왜 이렇게 설계하는가?)
- 데이터 흐름 다이어그램 (ASCII)
- DB 변경 사항 (마이그레이션 SQL + RLS)
- UI 변경 사항 (화면 레이아웃 ASCII)
- API/Edge Function 설계 (필요 시)
- 영향 범위 분석 (기존 코드 변경 목록)

3. **마지막 Phase**는 항상 "문서 동기화" (🏛️ Architect)
4. 각 Phase는 **독립 빌드 가능**해야 한다 (Phase 단위 커밋)
5. Phase 당 **예상 공수** 명시

### 7️⃣ 세션 종료 처리 (중단 시)

기획을 한 세션에 완료하지 못한 경우, 반드시 다음을 수행한다:

1. **Status 갱신**: 현재 진행 상황에 따라 `Draft` 또는 `In Progress`로 설정
2. **Planning Log 기록**: 문서 내 `## 12. Planning Log` 섹션에 세션 기록 추가
3. **Last Updated 갱신**: 헤더의 날짜를 현재 날짜로 갱신
4. **문서 버전 증가**: 의미 있는 변경이 있으면 버전 번호 증가
5. **커밋**: `commit-bot` 스킬로 문서만 커밋

**세션 종료 보고 형식 (기획 미완료 시)**:

## 연속 실행 옵션

### 기획 완료 시 (Status: Approved)
1. **바로 블루프린트 등록**: `/plan-to-blueprint` 워크플로우 실행
2. **기획 문서 검토**: 사용자가 먼저 리뷰한 후 등록
3. **추가 기획 작성**: 다른 기능의 기획도 작성

### 세션 중단 시 (Status: Draft / In Progress)
1. **다음에 이어쓰기**: `/plan` 실행 시 자동으로 기존 문서 감지됨
2. **기획 수정**: 특정 섹션만 수정/보완 요청
3. **기획 폐기**: 더 이상 진행하지 않을 경우 파일 삭제

## 주의사항

- ❌ 이 스킬을 Architect 이외의 에이전트가 수행하지 않는다
- ❌ 기획 문서 작성 중 코드를 변경하지 않는다
- ❌ 현황 분석 없이 기획 문서를 작성하지 않는다
- ❌ 에이전트 배분 없이 Phase를 정의하지 않는다
- ❌ 기존 기획과 중복되는 기획을 새로 작성하지 않는다
- ❌ 사용자의 요구사항이 불명확한데 추측으로 기획하지 않는다 (반드시 확인)
- ✅ 기획 문서는 항상 `.docs/planning/`에 저장한다
- ✅ 실제 코드/DB를 분석한 결과를 As-Is에 반영한다
- ✅ 모든 DB 변경에 실행 가능한 SQL을 포함한다
- ✅ 마지막 Phase는 항상 "문서 동기화" (Architect)
- ✅ 기획 완료 후 `commit-bot` 스킬로 문서만 커밋한다
